# Писма при поръчка — какво трябва да се направи

Кодът е готов и проверен. Остават три неща, които изискват достъп до твои
акаунти — затова не мога да ги свърша аз.

## Как работи

```
Количката (браузър)
      │  POST /api/order  { само SKU и количество, БЕЗ цени }
      ▼
api/order.js  (функция във Vercel)
      │  преизчислява сумите по api/_catalog.json
      │  сглобява двете писма от api/_emails.js
      ▼
Resend API
      ├──► писмо до магазина     (ORDER_TO)      — всички данни за поръчката
      └──► писмо до клиента      (неговия имейл) — „Благодарим за поръчката"
```

Цените **никога** не се вземат от браузъра. Клиентът праща само `sku` и `qty`;
сумите се смятат наново по каталога. Иначе всеки може да си отвори конзолата
и да поръча за 0,01 €.

Ако функцията не отговори, количката пробва стария релей `formsubmit.co`, а
ако и той не успее — показва връзка „изпратете поръчката по имейл“. Поръчка
не се губи мълчаливо.

## 1. Resend

1. Регистрация на [resend.com](https://resend.com) — 3000 писма/месец безплатно.
2. **Domains → Add Domain → `asiansecret.bg`.**
3. Resend дава няколко DNS записа (SPF, DKIM, а понякога и DMARC). Добавят се
   там, където се управлява DNS зоната на домейна.
4. Изчаква се да светне „Verified“.
5. **API Keys → Create API Key**, с права само за изпращане.

> Без верифициран домейн Resend отказва да праща от адрес на този домейн.
> Затова `zax12@abv.bg` **не може** да бъде подател — домейнът `abv.bg` не е
> твой. Той е сложен като `reply_to`, така че отговорите на клиентите пак
> идват при теб.
>
> Ако се верифицира поддомейн, подателят става `orders@send.asiansecret.bg`.
> Ако се верифицира главният домейн — `orders@asiansecret.bg`.

## 2. Променливи на средата във Vercel

Project → Settings → Environment Variables:

| Име | Стойност |
| --- | --- |
| `RESEND_API_KEY` | ключът от стъпка 1 |
| `ORDER_TO` | `kaloian8000@gmail.com` |
| `ORDER_FROM` | `Asian Secret <orders@asiansecret.bg>` |

След добавяне се пуска нов deploy, за да ги вземе.

## 3. DNS на домейна — ГОТОВО

Проверено на 22.08.2026: домейнът се резолвва (217.65.159.114), сайтът
отговаря с 200 на всички адреси, а имената на сървърите са на Hostinger
(`apollo/athena.dns-parking.com`). **DNS зоната се редактира в hPanel на
Hostinger**, не в SuperHosting.

Текущо състояние на пощенските записи:

| Запис | Стойност | Внимание |
| --- | --- | --- |
| MX | `mx1.hostinger.com`, `mx2.hostinger.com` | пощенската кутия на домейна — **не се пипа** |
| SPF (TXT) | `v=spf1 include:_spf.mail.hostinger.com ~all` | **вече съществува** |
| DMARC | `v=DMARC1; p=none` | остава както е |
| DKIM за Resend | липсва | добавя се на стъпка 1 |

> **Един домейн = един SPF запис.** Ако Resend поиска SPF на главния домейн,
> include-ът се **добавя в съществуващия ред**, не се прави втори TXT. Два SPF
> записа не се събират — и двата стават невалидни и писмата отиват в спам.
>
> Затова по-безопасният вариант е Resend да верифицира **поддомейн**
> (`send.asiansecret.bg`): тогава SPF и MX на главния домейн изобщо не се
> докосват и пощенската кутия остава недокосната.

## Полезни команди

```bash
# преглед на двете писма в браузър (нищо не се праща)
PREVIEW_BASE=http://localhost:8793 node tools/preview-emails.mjs
# после се отварят tmp/email-customer.html и tmp/email-owner.html

# проверка на логиката, също без изпращане
node tools/test-order.mjs

# каталогът за сървъра се пресъздава заедно със страниците
node tools/seo-build.mjs
```

## Ако хостингът се окаже с PHP

Тогава функцията може да живее на същия домейн вместо във Vercel — отпада
нуждата от CORS и от отделен адрес. Логиката е същата, но трябва да се пренапише
в PHP. Кажи, ако се стигне дотам.

## Какво остава без покритие

- **Няма съхранение на поръчките.** Ако и двата начина за изпращане паднат,
  поръчката съществува само в писмото, което клиентът може да изпрати ръчно.
- **Няма ограничение на заявките.** Функцията праща писмо до адрес, подаден от
  посетителя. Има капан за ботове и валидации, но при истински спам ще трябва
  ограничител по IP.
